# ADR-0012 — M2 tenant-private driver registry and engagement boundary

Accepted for the first M2 vertical slice, following the owner's authorization to proceed after the design review. Existing M1 behavior and ADR-0010/0011 design remain foundations.

DriverIdentity belongs to one tenant, distinct from login users and employer engagements. Collect only a company driver reference and names for this synthetic slice; no DOB, SSN, license number or screening data. A tenant-scoped reference is unique, immutable through ordinary operations, and never inferred from names. Same-name records remain separate. Explicit reference conflicts require investigation rather than merge; merging is not implemented by this slice.

DriverEngagement records retain branch, start/end dates, operational state and version. Branch transfer closes the old engagement and creates another, preserving prior relationships. One current engagement per tenant-private identity is enforced by a partial unique index. Rehire creates a new engagement after the former one ends. State changes are explicit, versioned, locked, audited commands, never legal eligibility decisions. Transfers and identity corrections require whole-company authority; corrections record a verified basis and reason.

Extend current relationship-based authorization with explicit driver capabilities: client administrators/contributors and assigned specialists/reviewers can read/write; viewers read only; whole-company client administrators and assigned reviewers can correct/transfer. Integration administrators and provisioning administrators receive no implicit driver access. Company metadata exposes an additive nullable driver_access capability summary derived from current real grants. Backend services recheck every command. Branch-scoped users see only their own current/historical engagements; they cannot infer a destination branch after transfer. Full identity history is whole-company only. Existing organization audit endpoints must not expose sensitive driver event details to provisioning-only roles.

Creation requires an actor/tenant-scoped command UUID. A protected payload hash plus resource identifier records idempotent replay; changed payload under the same key is rejected. Every replay rechecks current scope. Names alone never deduplicate. Transactions include driver/engagement/history/audit; optimistic versions and database constraints prevent duplicate current engagements and conflicting corrections.

M2 continues afterward with requirement/policy versions and private S3 quarantine/evidence/review. Do not expose fake document controls, generic legal compliance scores or successful malware checks. This registry slice does not complete M2. Preserve the approved original visuals in a scoped roster and identity/engagement workspace, using real states and compact forms/tables.

Search uses an authenticated POST body so names/references do not enter query URLs. Read-only grants remain sufficient to search, with normal origin/CSRF validation. Full history additionally requires whole-company audit authority. Transfer dates close the previous and start the new engagement on the same effective date; unscheduled future transfer/end commands are rejected, and activation cannot precede a future start. Explicit rehire requires whole-company write authority. These are operational consistency guards, not invented legal eligibility rules.
