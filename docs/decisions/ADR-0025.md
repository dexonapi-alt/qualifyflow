# ADR-0025 — Connected driver work and truthful feedback

2026-11-19. The owner approved improving next actions, ownership, connected inspectors, activity, empty states and action feedback, starting with the driver journey. Extend the approved shell, personal profile and centered identity interaction. Do not redesign navigation or advance milestone scope.

## Decision

Use the existing authorized qualification-file response to derive one prioritized next step: attention before missing evidence, then processing/review, then completed evidence. Inspect the latest evidence version to distinguish quarantine/scanning, scan problems, requests for information and escalation. The server's requirement state remains authoritative, including a previously accepted version remaining current while a newer version is being scanned. Never infer driving eligibility, overall onboarding completion or an assigned specialist.

Carry persisted company intake/review responsibility into the profile. Label this as responsibility, not a claim that an individual is actively working. Unknown values say Not configured. Existing server capabilities still govern upload/review and tenant/branch access; responsibility labels do not grant or revoke permissions.

Introduce a reusable native-dialog detail panel. Opening a requirement keeps the source profile mounted and reuses QualificationFile's real upload, scan, review and follow-up operations, filtered to the exact requirement. Full-file navigation remains available and preserves exact requirement focus. Escape, backdrop and Close details dismiss; explicit Tab wrapping, focus restoration, scroll locking and mobile full-width presentation are required. No new dependency or fabricated inspector actions.

Successful server mutations followed by refreshed file state update the underlying profile immediately. Confirmation must survive removal of a submitted review/follow-up form. Failed operations retain errors and do not claim success. Poll only actual pending security scans while the document is visible; guard stale responses and expose refresh failures rather than silently treating them as empty data.

Evidence processing milestones show recorded receipt, scan and review timestamps. A failed scan is attention, not successful completion. The activity preview combines authorized driver history and current-engagement evidence receipts/review outcomes; unknown upload actors are not invented. Each event opens its real recorded context and full detail. The full record history and complete evidence version history remain accessible.

## Boundaries

Frontend only: no backend authorization, API contract, migration, audit record, legal decision, external notification or tenant membership change. Synthetic QA records only. This establishes reusable panel/activity/milestone patterns; it does not claim every work queue has been migrated or all milestone exits are complete. Canonical color meanings, Inter, icon family, current shell and reduced-motion behavior remain.

## Evidence

Executed verification and limitations are recorded in docs/design/CONNECTED_DRIVER_EXPERIENCE.md and the implementation context. Tests must include actual upload → security scan → review → refreshed profile, error recovery, keyboard focus and the four supported viewport widths. An attractive screenshot alone is insufficient.
