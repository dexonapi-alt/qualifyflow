# ADR-0019 — Truthful local provider connection and signed intake

Implement the first provider adapter as a separate loopback-only synthetic simulator, with real authenticated HTTP account tests and report pulls. Connection state distinguishes configured, test_failed, sandbox_verified and paused; it never means a commercial provider or production connection. No arbitrary endpoints, DNS destinations, redirects or production credentials. Simulator transport is fixed to127.0.0.1 with a configured bounded local port. No new dependency is required.

Whole-company employer administrators configure/rotate/test the connection and approve its scope. Delegated provider intake is bound to that employer owner and checked against current active membership/tenant/connection status on each receipt and job. Provisioning-only administration does not imply report or connection-secret access. Assigned staff can inspect sanitized diagnostics. Provider access credentials and incoming webhook signing keys remain distinct, encrypted, never included in list/read/log responses. Rotation invalidates prior tests/signatures as appropriate.

Signed incoming webhook verifies timestamp, HMAC and bound account/client before canonical intake. A unique connection/event ID plus canonical envelope fingerprint rejects changed replay; exact retries return the original receipt. Preserve encrypted original provider envelope separately from normalized canonical metadata. The canonical CSV receipt/worker pipeline is shared rather than fabricating accepted reports. Successful reception means durable intake, not matched/accepted evidence. Pull cursors advance only with committed reception.

This is a local synthetic integration slice, not completion of all M5. Commercial connector contracts, external credentials, machine client APIs and production operations require separate exit evidence. Owner authorizes continued local implementation, not public deployment or external messages.


Durable pull jobs now use PostgreSQL leases, bounded retry/backoff/jitter and recorded terminal failures. Explicit employer-approved interval schedules support no-write dry runs, pause and credential-bound current authorization. Both native worker and Celery register these handlers. This is one narrowly scoped automation type, not a general rules engine.
